Several problems were found through the data-quality checks. In asset_weekly, there were duplicate rows in that table (42), and asset_registry had no duplicates. No leading or trailing spaces were found in asset_id.

There were multiple categorical variables with inconsistent labels. For instance, among the available options for operatin_mode, the possible values were “Auto”, “AUTO”, and “automatic”, and similar inconsistencies were seen for the region, vendor and criticality.

Q3

Two trends observed in the exploratory analysis may be better explained by tree-based modelling.

First, the relationship between operating load and incident risk is non-linear. The incident rate for the Low and Medium load groups is quite similar (approximately 12%), but the High load group has a noticeably higher rate of around 18.7%. A tree model will account for this kind of effect with a split at a certain level of load, while a simple additive linear model will take gradual linear dependence into account unless additional terms are introduced.

Second, it seems that there is a possible interaction between load and vibration. The highest rate of incidents takes place when both load and vibration are high (27.7%), while the effect of vibration varies in different load groups. This effect can be captured by a tree model easily, while a simple additive linear model would require additional interaction terms.

log_loss <- function(actual, prob) {
  
  prob <- pmin(
    pmax(prob, 1e-15),
    1 - 1e-15
  )
  
  -mean(
    actual * log(prob) +
      (1 - actual) * log(1 - prob)
  )
}


roc_auc <- function(actual, prob) {
  
  n_pos <- sum(actual == 1)
  n_neg <- sum(actual == 0)
  
  ranks <- rank(
    prob,
    ties.method = "average"
  )
  
  rank_pos <- sum(ranks[actual == 1])
  
  auc <- (
    rank_pos - n_pos * (n_pos + 1) / 2
  ) / (n_pos * n_neg)
  
  auc
}


class_metrics <- function(actual, prob, threshold = 0.5) {
  
  pred <- ifelse(
    prob >= threshold,
    1,
    0
  )
  
  TP <- sum(pred == 1 & actual == 1)
  TN <- sum(pred == 0 & actual == 0)
  FP <- sum(pred == 1 & actual == 0)
  FN <- sum(pred == 0 & actual == 1)
  
  sensitivity <- TP / (TP + FN)
  specificity <- TN / (TN + FP)
  
  c(
    sensitivity = sensitivity,
    specificity = specificity
  )
}

Log_loss is a metric that assesses the quality of probabilities produced by the predictions made and penalises overly confident false predictions.

ROC AUC is a metric that assesses how well the model ranks the incidences correctly over the incidents.

At a threshold of 0.5, the sensitivity is the percentage of correctly identified incidence and the specificity is the percentage of correctly identified non-incidents.

All these metrics will be useful in checking the performance of the final Random Forest and the XGBoost models.

With the utilization of early stopping, a total of 6 boosting rounds were performed i.e. The CV run stopped at round 26 after 20 further rounds without improvement., and the least cross-validation log loss value was found to approximately be equal to 0.3673.

The cross-validation procedure finished at 26 rounds since the best performance was achieved in round 6, and there were no improvements in the following 20 rounds.

Early stopping is critical in the case of boosting, as any new tree is fitted one after another due to the intention to improve the updated model. If boosting is applied for several rounds, it is possible for the model to start fitting noise present in the training dataset.

This was illustrated in Question E1, where the training log loss continued to go down after round 6, while cross-validation log loss started to grow.

In the case of a random forest, trees are fitted independently, and their predictions are simply averaged together. Generally, using more trees gives more stability to the entire ensemble rather than allowing it to get used to the training data in the course of time. Thus, the number of boosting rounds would have a more direct impact on the model complexity than the number of trees within the random forest.

F-2

Both Random Forest and XGBoost employ decision trees but with different forms of overfitting.

In a Random Forest, several trees are built from different random samples of data (called bootstraps) and random subsets of predictors, and the predictions from each tree are combined, or averaged. This averaging helps prevent serious overfitting when you add more trees to the model. This is reflected in our results by observing that the OOB error remained between 12.9% and 13.1% as the number of trees increased.

XGBoost sequentially fits trees. New trees are added to correct the errors of the existing ensemble. With too many rounds of boosting, the model will be able to fit noise in the training data increasingly well.

The flexible XGBoost model was evident in this. The optimal cross validation log loss was obtained around round 6, but training log loss still kept on reducing and cross validation log loss kept on increasing. As we can see, the more boosting rounds we added, the more overfitting we did.

F-3

In a Random Forest, the number of independently fitted trees in the ensemble is controlled by num.trees. The trees are averaged together, so increasing num.trees usually increases the stability of the predictions, and decreases random variation. In our analyzes, increasing the number of trees from 50 to 1000 did not lead to a large increase in OOB error.

In XGBoost the number of trees are controlled by nrounds , which is the number of trees added sequentially. Each new tree is fitted to fix the mistakes in the current model. Thus, increasing nrounds directly increases the complexity of the boosted model and may cause overfitting if we boost for too many rounds.

These two parameters shall not be interpreted in the same way. Adding more trees in Random Forest mainly improves stability through averaging. Adding more boosting rounds in XGBoost continues to change the fitted model and eventually leads to a decrease in performance on unseen data.

F-4

Another form of overfitting is to look at the final test set over and over again when you try different model settings.

Repeated use of the test set in model selection will cause information from the test data to leak into the decision of which model to select. The selected model might then perform especially well on that particular test set, but not necessarily on truly new data. This results in an overly optimistic report of test performance.

To reduce this problem hyperparameter tuning and model selection should be done using only the training data, for example with cross-validation or out-of-bag error. Keep the final test set aside and use it only for evaluation after all modeling decisions are made.
